# Wealth ingestion

Sarwa wealth is a provider-native snapshot feed. It is not transaction ingestion and it does not create synthetic spending rows. The first registered source is the authenticated capture at `runtime/browser-captures/sarwa-holdings-2026-08-18.json`.

## Acquisition contract

Sarwa refresh is intentionally user-assisted. The provider recipe opens the login page, the user completes login and MFA, and the agent captures the visible holdings into the versioned source shape. No password, OTP, cookie, token, session, or full account number may enter a recipe, capture, manifest, or log. There is no unattended Sarwa refresh claim.

The capability result is therefore:

- status: `USER_ASSISTED_REQUIRED`;
- acquisition: `USER_ASSISTED_BROWSER_CAPTURE`;
- cookie and credential persistence: disabled;
- official API/export and unattended refresh: not supported unless a future, separately verified provider implementation changes the versioned capability record.

`as_of` describes the market value date. `captured_at` describes when the browser evidence was collected. A snapshot becomes `STALE` after the configured seven-day interval even when all of its arithmetic still reconciles.

## Data contracts

- `config/wealth-snapshot-schema-v1.json` stores stable portfolio identity, values, cash, positions, instrument identity, units, computed display price, return data, activity availability, source identity, and reconciliation.
- `config/fx-snapshot-schema-v1.json` stores the exact conversion pair, time, rate, precision, freshness allowance, provider, and source identity used for an AED projection.
- `config/account-completeness-schema-v1.json` separates immutable provider account identity from mutable display names.
- `config/wealth-sources.json` maps safe capture labels to stable opaque identities and records interactive provider capability.
- `config/account-completeness.json` is the scoped expected inventory for FAB non-credit accounts and Sarwa.

The same completeness contract retains the closed ADCB credit-card account for
history only. It is inactive, excluded from live routing, and must reconcile to
exactly AED 0. A non-zero balance is a validation failure; no balancing row is
generated by this module.

The existing Sarwa capture parses to five portfolio records. Four active portfolios are proposed as off-budget Actual investment accounts. The zero-balance closed Sarwa Classic account is retained in completeness checks but excluded from the Actual proposal. Black Swan Protection is insurance coverage, not an asset, and is excluded from net worth.

## Reconciliation

Each Invest portfolio checks `sum(position market values) + cash = portfolio total`. Sarwa rounds displayed components, so a difference up to USD 0.05 is `RECONCILED_WITH_ROUNDING`; a larger difference blocks projection. Trade positions were not available, so Trade is explicitly `COMPONENTS_UNAVAILABLE` rather than falsely reconciled at position level.

The sum of all five Sarwa portfolio totals, including Trade and the closed zero-value account, must equal the overall balance exactly. The registered capture reconciles to USD 1,571,611.22 with a USD 0.00 difference.

## Actual projection boundary

`build_actual_wealth_proposal` emits a review-only aggregate account proposal. It never calls Actual. Position rows remain outside the ordinary Actual ledger and are preserved in `config/proposals/sarwa-position-sidecar.json`. A conversion requires a fresh USD/AED `FXSnapshot`; without one, every AED initial balance remains null and the proposal is blocked.

The checked-in proposal at `config/proposals/actual-accounts-fab-sarwa.json` is deliberately blocked by non-FAB gates. The authenticated FAB inventory is complete as of 2026-08-19 and contains five deposit accounts plus one mortgage. For account 2001, the source-dated AED 225,011.45 balance minus AED 109,956.72 net activity in the 100 captured rows yields an AED 115,054.73 opening anchor immediately before 2026-05-06. The captured rows then follow that anchor exactly once. The four other zero-balance deposit accounts are retained as zero opening anchors. The AED 2,605,952 mortgage is proposed as an off-budget liability with a signed AED -2,605,952 opening anchor. These are account opening balances, not post-import adjustments; no synthetic balancing row or fabricated history is permitted.

`scripts/generate-account-proposals.py --evaluated-at <ISO timestamp> --check` deterministically proves that both checked-in proposals still match the immutable captures. Changing the evaluation timestamp exercises the future and stale gates without mutating Actual.

## Remaining user-assisted evidence

1. Refresh Sarwa interactively when the seven-day source window has expired, capturing the same portfolio summaries, cash, and position fields. No session state is retained.
2. Supply or capture a timestamped USD/AED FX observation close enough to the Sarwa valuation timestamp for reviewable AED projection.
3. Supply the issuer-evidenced ADCB closing payment/statement and a read-only Actual account readback. The closed historical card passes only if both show exactly AED 0 and Actual marks it closed; no correction row is generated.
